# Storage Decommissioning Plan (Hamilton‑First Warehouse)

## Why this doc exists

We have fully implemented the Hamilton‑first warehouse design, but storage still contains legacy or
compatibility surfaces that:

- keep storage coupled to `codeintel.build.*`,
- duplicate the “single I/O boundary” principle (writes and SQL execution outside `Warehouse`),
- preserve old, constant-based view-name modules and other shims,
- keep niche utilities that no longer fit the new introspection + profiling story.

This plan turns that into an explicit, staged checklist with acceptance criteria and verification
steps so we can land the decommissioning safely.

## Definition of done (acceptance criteria)

### Architecture invariants

- [ ] `rg -n "from codeintel\\.build|import codeintel\\.build" src/codeintel/storage` returns **0 hits**.
- [ ] Storage provides no “bridge” layer for build contracts (no `build_bridge.py` and no equivalent
      that imports build).
- [ ] All writes in build/serving/etc go through `Warehouse` (or a storage-owned façade that is
      implemented in terms of `Warehouse`).
- [ ] All non-trivial SQL/DDL is generated by Ibis + SQLGlot; direct `con.execute(...)` usage remains
      constrained to the storage internals policy/session execution surface.

### Deletions / removals expected

- [ ] Deleted: `src/codeintel/storage/build_bridge.py`
- [ ] Deleted: `src/codeintel/storage/gateway_cache.py`
- [ ] Deleted: `src/codeintel/storage/validation/data_checks.py`
- [ ] Deleted: `src/codeintel/storage/gateway/insert_helpers.py`
- [ ] Deleted: `src/codeintel/storage/queries/execution.py`
- [ ] Deleted: `src/codeintel/storage/helpers/profiling.py`
- [ ] Deleted: `src/codeintel/storage/view_names.py`
- [ ] Deleted: constant-only modules under `src/codeintel/storage/views/*_views.py`
- [ ] Deleted: `src/codeintel/storage/datasets/scaffold.py` and `tests/storage/test_dataset_scaffold.py`
      (if scaffolding is no longer part of the workflow)
- [ ] Removed: `IbisGateway.sql` escape hatch in `src/codeintel/storage/ibis_adapter.py`

### Quality gates

- [ ] `uv run python -m tools.quality_report --output build/quality-results/quality_report.json` passes
      with 0 Ruff/Pyright/Pyrefly errors.
- [ ] `uv run pytest -q` passes.

## Ground rules for execution

- Prefer making **shared primitives** live in `codeintel.core` or a new top-level shared package
  (e.g., `codeintel.hamilton`) rather than keeping them build-owned.
- Remove runtime storage→build dependencies by moving primitives “down”, not by adding new shims.
- Keep steps small enough that failures are easy to attribute (phase-by-phase).
- After each phase: run quality gates.

## Current legacy / compatibility inventory (what we are removing)

### Confirmed legacy/compat in storage

- `build_bridge` (storage→build contract/schema/validation shim): `src/codeintel/storage/build_bridge.py`
- `validation/data_checks.py`: pure re-export shim of `storage/queries/safe.py`
- `views/creation.py`: accepts raw DuckDB connections “for compatibility”
- Constant-only view name modules + aggregator: `src/codeintel/storage/views/*_views.py`,
  `src/codeintel/storage/view_names.py`
- `DatasetRegistry` compatibility aliases: `mapping/jsonl_mapping/parquet_mapping/table_for_name/meta`
- `IbisGateway.sql`: raw SQL escape hatch
- `gateway_cache.py`: unused global cache surface
- `gateway/insert_helpers.py` + accessor `insert_*` methods: duplicate write surface
- `queries/execution.py`: low-level SQL execution surface used by serving/search
- `helpers/profiling.py`: niche EXPLAIN/ANALYZE tooling for two docs views

### Extra items from the other review (validated)

- `datasets/scaffold.py`: a scaffolding tool used only by tests; CLI command exists but does not call it.
  If scaffolding is no longer part of the workflow, delete it and the test.
- `queries/execution.py`: should be removed once serving/search is migrated to a storage-owned backend/
  policy execution surface.
- `gateway/insert_helpers.py`: should be deleted once Warehouse is the only write boundary.

## Implementation plan (phased)

- [ ] Add an architecture test: “no `codeintel.build.*` imports inside `src/codeintel/storage/`”.

## Risk & sequencing notes

- The hardest steps are Phase 2 (moving contract/schema authority out of build) and Phase 5 (removing
  gateway accessor write APIs). Do Phase 1 first to make Phase 2 feasible.
- View-name constants removal (Phase 3) can ripple into build schema compilation and config modules;
  treat it as its own PR-sized step even if you’re doing all this at once.
- Avoid leaving partial “re-export” layers indefinitely; use them only as a temporary bridge during a
  phase, then delete.
